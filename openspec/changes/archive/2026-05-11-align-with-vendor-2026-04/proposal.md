## Why

Назрел минимальный апдейт по двум направлениям:

**A. Код конфигурации 1С устарел на alcor.** Локальная staging переехала: отчёты теперь в `~/LISmcp/report/` (сегодня), а файлы — в отдельных проектах `~/Проекты/ЛИС1С/` и `~/Проекты/ЕвротестРасширение/` (29.04). На alcor в `~/mcp/{LISreport,LISfiles,extensions/Евротест}` лежит снимок от 21.03. Серверы CodeMetadata и Graph работают на устаревших индексах. Желательна **инкрементальная** переиндексация без `RESET_DATABASE` — изменения относительно небольшие, и согласно анонсу вендора 15.04.2026 фоновая индексация работает по факту, плюс fallback покрывает временную неконсистентность.

**B. Вендорское обновление образов.** Вендор 10.05.2026 выпустил bug-fix релиз поверх большой апрельской поставки (15.04). Согласно его сообщению — переиндексация существующих баз НЕ требуется, образы взаимозаменяемы при сохранении volumes. INSTALL.md в дистрибутиве (шаг 1.8) явно описывает **реактивную** модель ключей: обновлять `LICENSE_KEY_*` ТОЛЬКО при ошибке `license invalid` в логах после рестарта.

Архитектурный выбор (`mcp-deployment/` vs полный отказ vs slim-обёртка) зафиксирован в [auto-memory architecture_decision_2026-05.md](../../../.claude/projects/-home-l7777---------mcp/memory/architecture_decision_2026-05.md) как **путь 2 — slim-mcp-deployment** в отдельный будущий change. Здесь не делаем.

OneMCP.cfe (расширение «AI ↔ живая база 1С» из вложенного `MCP_1C_Distr.zip`) — отдельная история, не серверная. См. [auto-memory onemcp_cfe_followup.md](../../../.claude/projects/-home-l7777---------mcp/memory/onemcp_cfe_followup.md).

## What Changes

### A. Sync свежей выгрузки 1С на alcor + перезапуск

- rsync (с `--delete`, после dry-run для проверки):
  - `~/LISmcp/report/` → `alcor:~/mcp/LISreport/` (отчёты)
  - `~/Проекты/ЛИС1С/` → `alcor:~/mcp/LISfiles/` (основная конфигурация)
  - `~/Проекты/ЕвротестРасширение/` → `alcor:~/mcp/extensions/Евротест/` (расширение)
- `docker compose restart 1c-metadata 1c-graph-metadata` (без `RESET_DATABASE`)
- Контроль через логи: фоновая индексация подхватит изменения (15.04 анонс), fallback во время индексации сохраняет доступность (тоже 15.04 анонс)
- Если фоновое обновление не справится (висячие ноды Neo4j от удалённых объектов и т.п.) — fallback на полный reset с предупреждением

### B. Вендорское обновление (реактивная модель)

- Сделать `~/mcp/mcp-deployment/.env.bak.YYYYMMDD` (страховка)
- `docker compose pull` для всех сервисов в `mcp-deployment/`
- `docker compose up -d` (recreate с новыми образами, volumes сохраняются)
- Подождать ~30 секунд, проверить логи на `license invalid` / `401` / `unauthorized`
- ТОЛЬКО при ошибке ключа — обновить соответствующий `LICENSE_KEY_*` из `MCP_Distr/config.env` (там персонализированные ключи из личного кабинета пользователя)

### C. Минимальный cleanup репо

- `MCP_Distr.zip` → `.gitignore` (тяжёлый бинарник, потенциально содержит персональные ключи в config.env)
- Распаковать актуальный `MCP_Distr.zip` в `MCP_Distr/` с заменой структуры (`.gitignore` уже скрывает `MCP_Distr/`, но локальная зеркальная копия должна отражать актуальное)
- НЕ удалять корневые `FormsServer/` и `Graph_metadata_search/` (legacy от первого дистрибутива, но безвредно лежат; уборка — отдельный change в рамках slim-mcp-deployment)
- НЕ менять `mcp-deployment/` структуру — это задача отдельного будущего change

### Не делаем сейчас

- Миграция на `:light` образы (требует переиндексации из-за смены размерности векторов; экономия 7+ ГБ, но не блокер)
- Удаление CloudEmbeddings из `mcp-deployment/docker-compose.cloud.yml` (не пользуемся, но удалять — отдельная аккуратная работа)
- Реструктуризация `mcp-deployment/` (slim-mcp-deployment как отдельный change)
- Установка OneMCP.cfe в продуктовую 1С (отдельный non-server change)
- Проактивная ротация ключей (вендор явно описывает реактивную модель в INSTALL.md)
- Связь с вендором по поводу «MCP для правил» из анонса 15.04 (упомянут, но в дистрибутиве отсутствует — нет блокера)
- Расширение ЛОДЭ — оставляем как есть от 21.03 (пользователь не упомянул среди обновлений)

## Impact

- **alcor data**: rsync обновит 3 директории (отчёты ~30 МБ, files ~90 МБ оценочно, extensions ~3 МБ); --delete уберёт удалённые объекты
- **alcor downtime**: рестарт metadata + graph ~30–60 сек; fallback во время фонового переиндекса означает фактический downtime минимален
- **Образы**: pull bug-fix релиза (10.05); риск низкий (вендор явно говорит no-break, no-reindex)
- **Репозиторий**: `.gitignore` для `MCP_Distr.zip`, обновление `MCP_Distr/` распаковкой
- **Риски**:
  - Инкрементальный апдейт может оставить «висящие» ноды в Neo4j → мониторим, при необходимости fallback на full reset
  - При pull новых образов внезапно может потребоваться обновление ключа — реактивно делаем из `config.env`
  - rsync `--delete` потенциально снесёт что-то непредвиденное → обязательный `--dry-run` перед боевым прогоном
- **Что будет легче в следующий раз**: ротация ключей реактивная, не каждый раз; обновления вендора через `docker compose pull` без специальной подготовки
