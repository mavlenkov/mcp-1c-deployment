## ADDED Requirements

### Requirement: Локальная зеркальная копия актуального вендорского дистрибутива

В репозитории SHALL поддерживаться каталог `MCP_Distr/`, отражающий **актуальную** структуру и содержимое последней поставки от вендора (`MCP_Distr.zip` в корне). При каждом обновлении содержимое каталога MUST полностью замещаться распакованным архивом, а не добавляться поверх старого — иначе появляются устаревшие файлы, которые путают агентов и людей.

#### Scenario: Получено новое обновление от вендора

- **GIVEN** в корне репозитория появился свежий `MCP_Distr.zip` от вендора
- **WHEN** мы интегрируем это обновление в репозиторий
- **THEN** содержимое `MCP_Distr/` SHALL быть полностью заменено распакованным архивом
- **AND** старые файлы с другой структурой (например, `*.txt` из предыдущей поставки) MUST быть удалены
- **AND** README или CLAUDE.md SHALL ссылаться на актуальный входной файл (например, `INSTALL.md`), а не на устаревшие файлы

#### Scenario: Структура дистрибутива от вендора изменилась

- **GIVEN** в новом архиве изменился набор файлов (например, появился `INSTALL.md` и `config.env`, исчезли некоторые серверы)
- **WHEN** мы обновляем `MCP_Distr/`
- **THEN** изменения структуры MUST быть зафиксированы в OpenSpec change как отдельный пункт обсуждения
- **AND** наши деплойменты (compose, скрипты, документация), ссылающиеся на старую структуру, SHALL быть проверены и обновлены

### Requirement: Реактивная ротация лицензионных ключей по сигналам сервера

Лицензионные ключи в `mcp-deployment/.env` SHALL обновляться **реактивно** — только когда соответствующий сервер вернул ошибку лицензии в логах после `docker compose pull && up -d`. Это согласуется с моделью, описанной вендором в `INSTALL.md` (шаг 1.8): «Если ошибка лицензионного ключа: ... скачайте актуальный ключ в личном кабинете». Превентивная ротация ключей при каждом обновлении MUST NOT выполняться, чтобы не вносить лишних изменений и не копировать чужие ключи (если архив был получен не из персонального кабинета).

#### Scenario: После `docker compose pull && up -d` сервер пишет в логах об ошибке лицензии

- **GIVEN** после обновления образов один или несколько сервисов выводят в логах строки `license invalid` / `401` / `unauthorized`
- **WHEN** мы открываем актуальный `MCP_Distr/config.env` (из персонального кабинета пользователя)
- **THEN** для каждого упавшего сервера соответствующий `LICENSE_KEY_*` в `~/mcp/mcp-deployment/.env` SHALL быть заменён значением из `config.env` с учётом маппинга имён (например, `LICENSE_KEY_DOCS` ↔ `LICENSE_KEY_HELP`, `LICENSE_KEY_METADATA` ↔ `LICENSE_KEY_CODEMETADATA`)
- **AND** перед правкой `.env` SHALL создаваться таймстампированный бэкап (`.env.bak.YYYYMMDD`)
- **AND** контейнер MUST быть пересоздан через `docker compose up -d <service>` (с `-f <compose-file>` для нестандартных compose-файлов)

### Requirement: Опциональная миграция между тегами образов с явным opt-in

Переход между тегами вендорских образов (например, `:latest` → `:light`) может быть несовместим с существующими данными (другая модель эмбеддингов = другая размерность векторов = переиндексация). Такая миграция MUST NOT выполняться неявно при `docker compose pull` или вместе с обычным обновлением ключей.

#### Scenario: Решение о переходе на :light образ

- **GIVEN** в новой поставке образ `:light` стал стандартом по умолчанию у вендора
- **WHEN** мы рассматриваем переход с `:latest` на `:light`
- **THEN** в OpenSpec change миграция SHALL быть выделена в отдельный opt-in блок tasks.md
- **AND** в design.md MUST быть явно указаны последствия: длительность переиндексации, изменение зависимостей (online vs offline), стоимостное влияние (API-расходы)
- **AND** пользователь SHALL принимать решение явно перед выполнением, а не как побочный эффект обновления
