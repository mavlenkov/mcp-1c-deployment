## Decisions

### Решение 1: Инкрементальная переиндексация без RESET_DATABASE

Анонс вендора 15.04 утверждает: фоновое обновление индекса работает, fallback во время индексации сохраняет доступность сервера, индексация распараллелена. Это снимает наш предыдущий страх «полная переиндексация = часы downtime».

`docker compose restart 1c-metadata 1c-graph-metadata` без `RESET_DATABASE=true` рассчитывает на:
- Сервер при старте сравнивает источник с индексом (через `AUTO_UPDATE_ON_STARTUP`)
- Изменения подгружаются в фоне, в это время отдаются результаты по старому индексу (fallback)
- Удалённые объекты помечаются tombstones и удаляются из индекса

**Риск:** Neo4j может оставить «висячие» ноды от удалённых объектов (известный класс проблем графовых баз). Если проявится — fallback на полный reset через `RESET_DATABASE=true` и рестарт graph; metadata тоже можно перезапустить с reset, но это не обязательно.

### Решение 2: Реактивная модель ключей

Вендорский INSTALL.md, шаг 1.8 (строки 215–217):
> Если ошибка лицензионного ключа: «Лицензионный ключ для `<сервер>` не принят. Скачайте актуальный ключ в личном кабинете: https://vibecoding1c.ru/»
> После получения нового ключа — обновить config.env и перезапустить контейнер

Это явная реактивная модель: ключ обновляется ТОЛЬКО при ошибке, не превентивно. Принимаем эту модель:

1. `docker compose pull` без правки .env
2. `docker compose up -d` для recreate
3. Через 30 сек — grep логов на `license` / `auth` / `401`
4. ЕСЛИ есть ошибка — sed-замена соответствующего ключа из MCP_Distr/config.env, рестарт сервиса
5. ЕСЛИ нет — сохраняем status quo

**Преимущество**: меньше операций, меньше шансов ошибиться, меньше шансов скопировать чужой ключ.
**Риск**: ключи в config.env должны быть «нашими» (из личного кабинета пользователя). Подтверждено пользователем — архив скачан из https://vibecoding1c.ru/.

### Решение 3: rsync с --delete и dry-run

Используем `rsync -avz --delete` с обязательным предварительным `--dry-run`:

- `--delete` — индекс должен соответствовать актуальному состоянию выгрузки. Удалённые объекты в источнике должны исчезать в цели (иначе индексер не узнает, что они удалены, и оставит висячие ноды).
- `--dry-run` — выводим diff перед боевым прогоном, пользователь смотрит, что именно изменится. Защищает от неожиданных удалений (например, если перепутали папки).
- `--exclude` для git-метаданных (`.git`, `.claude`, `.codex`, `AGENTS.md`, `CLAUDE.md`) — это не часть выгрузки 1С, не должно попадать на alcor.

### Решение 4: Не трогаем mcp-deployment/ структурно

Решение пользователя — отложить на отдельный change (см. memory/architecture_decision_2026-05.md). В этом change: только данные и образы, никакой переписи compose/scripts.

Соответственно `1c-graph-metadata` (а не `1c-graph`) — фактическое имя сервиса в текущем `docker-compose.graph.yml:39`. Используем как есть.

### Решение 5: Не трогаем `:latest` vs `:light`

Анонс 15.04 говорит, что :light теперь действительно лёгкий и рекомендуемый. Но переход требует переиндексации (другая размерность векторов: локальный E5 384 → облачный qwen3-embedding-8b). Даже с fallback это часовая операция плюс постоянная зависимость от OpenRouter.

В этом change: тег НЕ меняем. `image:` в compose-файлах остаётся тот же. После pull получаем bug-fix версию того же тега.

Опциональная миграция на :light — отдельный явный opt-in change, см. spec `vendor-distribution`, требование «Опциональная миграция между тегами образов».

### Решение 6: Cleanup репо — минимум

- `MCP_Distr.zip` → `.gitignore` (на случай git add . защита от заливки 190 КБ архива с персональными данными)
- `MCP_Distr/` уже в .gitignore — туда распаковываем для AI-агента (нашего же), чтобы у него было актуальное представление вендорского дистрибутива

Корневые `FormsServer/` и `Graph_metadata_search/` — оставляем (не помешают, чистка — в slim-mcp-deployment).

### Решение 7: Расширение ЛОДЭ — не трогаем

Пользователь не упомянул ЛОДЭ среди обновляемого. На alcor лежит от 21.03, отчёт тоже от 21.03. Оставляем как есть. Если индексеры пожалуются на расхождение — fallback в follow-up.

## Risks & Mitigations

| Риск | Вероятность | Влияние | Mitigation |
|---|---|---|---|
| rsync --delete сносит что-то неожиданно | Низкая | Среднее (полное падение индекса до восстановления) | Обязательный --dry-run + явное согласие пользователя на видимый diff |
| Висячие ноды Neo4j после инкрементального обновления | Средняя | Низкое (поиск может возвращать призрачные результаты) | Мониторим логи graph; если проблема — fallback на full reset graph |
| Pull bug-fix приносит несовместимый ключ | Низкая (вендор сказал no-break) | Низкое (один сервис offline до фикса) | Реактивная ротация из config.env, .env.bak для отката |
| Образ с патчем graph_run_patch.py не подхватит патч | Низкая | Среднее (graph.business_search опять сломается) | Проверяем шаг 6.4; если упало — поднимаем gh issue или временно откатываем образ через .env.bak |
| Изменение источников файлов (LISmcp/files → Проекты/<config>) ломает что-то на alcor | Низкая | Низкое (LISmcp/files на ноуте устарело, alcor про это не знает — только rsync делает разницу) | rsync с --delete синхронизирует as-is, ничего «не помнить» |

**Откатные точки:**
- После шага 4 (rsync применился, restart ещё не сделан) — откат через rsync обратной стороны (alcor → ноут не реалистично, но индексы не затронуты до restart). Безопасно.
- После шага 7 (restart с новыми данными) — `RESET_DATABASE=true` + рестарт даст полную переиндексацию с актуальными источниками, это «всегда выход».
- После шага 9 (pull + up -d) — откат через .env.bak (если что-то про ключи) или ручное `docker compose up -d --no-deps <service>` с пинном предыдущего тега.

**Что не откатится без боли:**
- Удалённые объекты в `--delete` rsync — если случайно снесли источник, восстанавливать из git-проектов на ноуте (они под git-контролем).
